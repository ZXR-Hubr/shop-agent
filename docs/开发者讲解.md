## 零、先看全貌（面试开场 30 秒）

**一句话定位**：这是一个「LLM + Function Calling + RAG」的电商智能客服 Agent，能查商品、查订单、建售后工单、答政策问题，支持多轮对话，并带评测与测试。

**技术栈**：Python 3.10+ / FastAPI / Pydantic / httpx / python-dotenv；前端原生 HTML+CSS+JS；pytest；模型走阿里云百炼 qwen-plus 的 OpenAI 兼容接口。

**模块分工（8 个 Python 文件）**：

| 文件 | 角色 | 核心职责 |
|---|---|---|
| `config.py` | 配置中心 | 从 `.env` 读所有参数，frozen dataclass 固化 |
| `runtime.py` | 运行时状态 | 可热切换的 Mock/API 模式（带线程锁） |
| `llm.py` | 模型网关 | OpenAI 兼容 `/chat/completions` + Mock 规则引擎 |
| `agent.py` | 大脑 | System Prompt + 工具调用循环 |
| `tools.py` | 手脚 | 4 个工具的 JSON Schema 与实现 |
| `rag.py` | 知识库 | 本地向量化 + 余弦检索 |
| `memory.py` | 记忆 | 按 session_id 存最近 20 条，TTL 过期 |
| `main.py` | 接口层 | 页面 + 5 个 REST 接口 |

**一次请求的数据流**：

```
浏览器 POST /api/chat {session_id, message}
   ↓ FastAPI 校验参数
Agent.chat：
   1. memory.get(session_id) 取历史
   2. messages = system + history + user
   3. 循环（≤5 轮）：llm.chat(messages, tools)
        - 无 tool_calls → 最终回答，跳出
        - 有 tool_calls → 本地执行工具 → 结果以 role=tool 回填 → 再调模型
   4. 只把 user/assistant 写回 memory
   ↓
返回 {reply, tool_calls, usage, latency_ms}
```

**关键设计**：模型不碰真实数据，只负责「选工具、填参数」；真实数据由本地工具返回，从根上降低幻觉。工具调用是可展开的，前端能看到模型每一步的决策。

## 零点五、双模式系统详解（重点，面试高频）

项目有 **Mock / API 两种模式**，我用**两套互补的机制**来实现切换。理解这两套的区别，是讲清这个项目的关键。

### 为什么要有两种模式？

- **Mock 模式**：用规则模拟「选工具 → 出答案」，零费用、离线可跑、结果确定 → 适合演示、单元测试、没 Key 时用。
- **API 模式**：真实调用 qwen-plus，展示真实的 Function Calling 能力 → 适合展示效果。
- 面试时两套都要能当场切换，体现工程完整度。

### 机制一：本地 bat 脚本切换（改配置文件 + 重启）

**它解决的场景**：你在自己电脑上跑，愿意重启服务。

**创建过程与原理**：

1. **先写核心逻辑 `switch_mode.py`**（Python 处理文本比 bat 可靠）：
   - 读 `.env` 全文 → `splitlines()`
   - 过滤掉所有旧的 `LLM_MOCK=` 行：`[ln for ln in lines if not ln.startswith("LLM_MOCK=")]`
   - 追加新行：`LLM_MOCK=1`（mock）或 `LLM_MOCK=0`（api）
   - 写回文件
   - 防御：切 API 时若 `.env` 里没有有效 Key，给出提示
2. **再用 bat 包装成双击入口** `切换为Mock.bat` / `切换为API.bat`：
   - 内容极简：`cd /d "%~dp0"` → 调 `.venv\Scripts\python.exe switch_mode.py mock|api` → `pause`
   - **踩过的坑**：bat 最初用中文 + UTF-8 + LF 换行，导致 Windows cmd 解析括号块错乱、双击闪退。
     最终方案：**bat 内容全部用纯 ASCII + CRLF 换行**，中文提示一律交给 Python 输出。这是 Windows 批处理的经典陷阱。
   - `pause` 是为了让窗口停留，能看到输出，不闪退。
3. **生效链路**：`.env` 的 `LLM_MOCK` → `config.py` 的 `_flag("LLM_MOCK")` → `settings.llm_mock` → 服务**启动时**读取 → **必须重启才生效**。

### 机制二：网页热切换（改内存状态 + 即时生效）

**它解决的场景**：线上部署在云端沙箱，改不了 `.env`，也不可能每次重新部署；面试现场要能一键秒切。

**创建过程与原理**：

1. **新增 `runtime.py`**：用一个模块级变量保存当前模式，用 `threading.Lock` 保证并发安全：
   ```python
   _mode = "mock" if settings.llm_mock else "api"   # 默认值来自 .env
   def get_mode(): ...      # 读
   def is_mock(): ...       # 判
   def set_mode(mode): ...  # 写，带校验：只能 mock/api，api 必须有 Key
   ```
2. **改造 `llm.py`**：把 `if settings.llm_mock:`（读死配置）改成 `if is_mock():`（读运行时状态）——这是热切换能生效的关键一行。
3. **改造 `main.py`**：
   - `health` 接口改读 `runtime.get_mode()`
   - 新增 `GET /api/mode`（查当前模式）和 `POST /api/mode`（切换模式，非法值返回 422/400）
4. **改造前端 `index.html`**：header 加一个模式切换按钮，`renderMode()` 根据模式改文字和颜色（Mock 黄、API 绿），点击就 `POST /api/mode`，即时刷新 UI。
5. **性质**：这是**内存里的运行时状态**，重启服务后会回到 `.env` 的默认值。所以两套机制互补——bat 改「默认值」，网页开关改「当前值」。

### 面试怎么讲这段（体现设计能力）

> 「双模式我做了两层切换：底层是一套运行时状态机，用锁保证并发安全，并暴露了 `GET/POST /api/mode` 接口，前端开关点击即热切换，不改配置、不重启，方便现场演示；同时保留了一套双击脚本，通过改 `.env` 的 `LLM_MOCK` 来设定服务的默认模式。这样既满足了线上演示的灵活性，又保留了本地配置的可控性。」

一句话带出：**状态管理 + 并发安全 + RESTful 接口 + 前后端联动 + 配置分层**，全是加分点。

## 一、三分钟项目介绍（可以直接照着说）

> 这是一个电商智能客服 Agent。用户在网页对话框里提问，后端用 FastAPI 接收，把问题交给大语言模型。
> 模型不会直接编答案，而是先判断该调用哪个工具：查商品、查订单、创建售后工单，或者检索客服知识库。
> 工具在本地执行，把真实数据返回给模型，模型再组织成自然语言回复。
> 整个会话按 session_id 保存最近 20 条消息，支持多轮追问。
> 项目还带了一套评测集和单元测试：35 条用例覆盖功能、边界、多轮、拒答、越权五类场景，
> 真实 API 模式下通过率 100%、工具准确率 100%、安全护栏拦截率 100%（5/5）；
> 指标拆成工具选择、回答事实、安全护栏三层，方便迭代时对比效果。评测用例还能在聊天界面里边用边攒。

## 二、开发流程复盘（按真实开发顺序讲）

### 第 1 步：拆需求，定义边界

先把「智能客服」拆成 4 类可执行的能力：

1. 商品咨询 → 需要商品数据 + 检索
2. 订单查询 → 需要订单数据 + 按订单号查
3. 售后办理 → 需要创建工单（写操作）
4. 政策问答 → 需要知识库 + RAG

这一步的产出是**工具清单**。工具定得好，Agent 的能力边界就清楚。

### 第 2 步：准备数据

- `data/products.json`：9 个商品，含类目、价格、库存、标签、描述
- `data/orders.json`：5 个订单，含状态、物流、金额
- `data/kb.json`：12 条客服规则

演示项目用 JSON 而不是数据库，是为了**零配置启动**；生产换成 MySQL / 接口即可，工具函数的入参出参不变。

### 第 3 步：写工具（先让工具能单独跑）

`app/tools.py` 里每个工具都是普通 Python 函数，可以单独测试：

```python
get_order("SO20261114002")   # {'found': True, 'status': '运输中', ...}
```

同时用 `TOOLS` 定义 JSON Schema，告诉模型每个工具叫什么、参数是什么、什么时候用。

### 第 4 步：写 Agent 循环

`app/agent.py` 是核心，逻辑只有 5 行伪代码：

```
messages = system + history + user
循环:
    结果 = LLM(messages, tools)
    如果没有 tool_calls: 返回结果
    执行 tool_calls，把结果以 role=tool 追加到 messages
```

### 第 5 步：接记忆

`app/memory.py` 按 session_id 存消息，只存 user / assistant，不存工具中间结果。

### 第 6 步：做 RAG

`app/rag.py` 把知识库文档转成向量，查询时做余弦相似度取 Top-3，作为 `search_faq` 的返回。

### 第 7 步：封接口 + 做页面

`app/main.py` 暴露 `/api/chat`，`static/index.html` 是一个原生 JS 聊天页，支持展示工具调用记录。

### 第 8 步：测试 + 评测 + 迭代

- `pytest`：24 个用例，覆盖工具、RAG、Agent、API + 5 个多实现验证（Redis/LangChain/向量库降级/Flask）
- `eval/run_eval.py`：35 条用例（5 类场景），输出 5 个指标

## 三、代码走读（按文件）

### `app/agent.py` — 大脑

- `SYSTEM_PROMPT`：定义角色、工具使用规则、追问策略、转人工兜底
- `chat()`：拼上下文 → 调模型 → 执行工具 → 回填结果 → 再调模型 → 写记忆返回

### `app/config.py` — 配置中心
- 所有参数来自环境变量 / `.env`；`_flag()` 解析布尔值
- 用 `@dataclass(frozen=True)` 固化，避免运行中被误改
- `LLM_MOCK` 未设置时，「有没有 Key」自动决定默认模式

### `app/runtime.py` — 运行时状态
- 模块级 `_mode` + `threading.Lock`，支持 Mock/API 热切换
- `get_mode` / `is_mock` / `set_mode`（带参数校验和 Key 检查）

### `app/llm.py` — 模型网关

- 统一走 OpenAI 兼容的 `/chat/completions`
- 默认对接阿里云百炼（DashScope）`qwen-plus`，换厂商只改 `.env` 两个变量
- Mock 模式：用规则模拟「选工具 → 出答案」，保证无 Key 可跑、测试确定性

### `app/tools.py` — 手脚

- 4 个工具函数 + `TOOLS`（schema）+ `TOOL_IMPL`（映射）
- 新增工具 = 写函数 + 加 schema，不改 Agent 代码

### `app/rag.py` — 知识库

- `_local_vector()`：字符 bigram 哈希 + 符号散列 + L2 归一化
- `embed_texts()`：有 `EMBED_MODEL` 走远程 API，否则本地
- `KnowledgeBase.search()`：余弦相似度排序取 Top-K

### `app/memory.py` — 记忆

- `get` / `append` / `clear`
- 内存字典或 Redis，最近 20 条

### `app/main.py` — 接口

- `GET /` 页面
- `GET /api/health` 健康检查（显示实时模式、模型、向量库）
- `POST /api/chat` 对话
- `POST /api/session/{id}/reset` 清空会话
- `GET /api/mode` 查询当前模式
- `POST /api/mode` 热切换 Mock / API（body: `{"mode":"mock"|"api"}`）

### `static/index.html` — 前端

- 消息气泡、快捷问题、工具调用折叠面板、新会话
- 右上角模式切换开关（点击调 `/api/mode`，即时生效）
- 用 `localStorage` 保存 session_id，刷新不丢上下文

## 四、关键设计决策（面试官最爱问「为什么」）

### 1. 为什么用工具调用，而不是把数据塞进 Prompt？

- 数据会变，Prompt 里塞死会过期；
- 数据量大时 Prompt 装不下，成本高；
- 工具返回的是**结构化事实**，能显著降低幻觉；
- 工具可以复用、可以单独测试。

### 2. 为什么工具结果要回填给模型，而不是直接返回给用户？

因为模型需要把「JSON 结果」翻译成用户能懂的话，还要结合上下文做追问、解释、引导。直接返回 JSON 体验很差。

### 3. 为什么记忆只存最终消息？

工具调用的中间结果又长又碎，存进去会：
- 快速吃满上下文窗口；
- 让模型被历史工具结果干扰。
只存一问一答，既保留语义，又控制成本。

### 4. 为什么本地向量库？

演示项目追求**开箱即跑**。本地向量化零依赖、离线可用。
`KnowledgeBase` 把「向量化」和「检索」解耦，生产换 pgvector / Milvus 只改存储层。

### 5. 为什么要做评测？

改 Prompt、换模型、加工具之后，需要知道「是变好了还是变坏了」。
把指标拆成工具准确率和关键词命中率，能定位问题出在「选错工具」还是「回答不对」。

### 6. 为什么限制工具轮数？

防止模型陷入「反复调工具」的死循环；同时给延迟和成本兜底。

## 五、高频追问 Q&A

**Q0-1：LLM 应用的安全怎么考虑？（新亮点）**
加了输入侧护栏 `app/guard.py`：正则识别两类高风险输入——① 提示注入 / 套取系统提示 / 角色劫持；② 隐私越权（查他人订单、批量客户数据、绕权限）。命中后由 Agent 直接返回拒答话术，**不进入 LLM 循环、不调用任何工具、不污染会话记忆**。评测里 5 条越权用例全部拦截（100%）。这是「LLM 应用」和「普通 CRUD」的区别之一。

**Q0-2：评测用例是怎么来的？能持续维护吗？（新亮点）**
两条来源：① 项目内置的 35 条用例，覆盖功能/边界/多轮/拒答/越权；② 聊天界面每条回复下的「+ 存为测试用例」按钮，把真实对话沉淀成用例（`POST /api/eval/cases` 写入 `cases.json`，标记 `source: ui`）。这样测试用例不是一次性写死的，而是随使用积累的回归资产——体现了「评测驱动迭代」的思路。

**Q1：怎么防止模型编造订单信息？**
订单类问题必须走 `get_order`，工具查不到就返回 `found: false`，Prompt 里明确「不要凭空编造」。评测里也有对应用例检查关键词。

**Q2：多轮对话怎么实现的？**
每次请求带上 session_id，服务端取出历史消息拼在 system 之后。前端把 session_id 存在 localStorage。

**Q3：用户不说订单号怎么办？**
Prompt 要求「信息不足时主动追问，一次只问最关键的问题」，模型会先问订单号。

**Q4：RAG 的召回不准怎么优化？**
三条路：换更好的 Embedding 模型；调整切分粒度；加关键词召回做混合检索。当前 12 条知识库规模小，本地向量够用。

**Q5：怎么保证工具参数正确？**
JSON Schema 约束类型和必填项；执行前用 `json.loads` 解析，解析失败给空参数；生产还应做业务校验（如订单号格式）。

**Q6：并发高了会怎样？**
内存会话不跨进程，需要换 Redis；LLM 调用要加超时、重试、限流；向量检索要换独立服务。

**Q7：手写循环和 LangChain 你为什么两个都做？**
两者我都在项目里真实实现了：`app/agent.py` 是手写 Function Calling 循环，`app/langchain_agent.py` 用 LangChain 的 `create_agent` + 同一批工具做了一套等价实现，`AGENT_FRAMEWORK` 一键切换。
手写的优势是链路透明、依赖少、每轮工具调用可精确控制，适合演示和排障；LangChain 的优势是生态和复杂编排（中间件、回调、多智能体）。
两套并存既能对比取舍，也说明我理解「框架不过是把循环封装了一层」——切换只改配置，业务工具完全复用。注意 LangChain 1.x 用 `create_agent`，老教程里的 `create_tool_calling_agent` 已废弃。

**Q8：这个项目最难的点是什么？**
不是调 API，而是**边界设计**：哪些问题必须查工具、查不到怎么兜底、什么时候追问、什么时候转人工。这些都在 System Prompt 和工具返回值里体现。

**Q9：怎么评估「回答质量」而不只是关键词？**
关键词只是低成本代理指标。更进一步可以加：人工标注评分、LLM-as-judge、任务完成率（是否成功创建工单）、多轮完成率。

**Q10：如果要做成生产系统，下一步做什么？**
Redis 会话、pgvector/Milvus、流式输出、鉴权限流、结构化日志与 Trace、Prompt 版本管理、敏感词与越权校验。

## 七、与简历描述的对应（四项技术已真实落地，可放心讲）

简历里写的技术点，项目里都做了**真实、可切换的实现**——不是挂名，是能当场切给你看的：

## 八、公网部署（加分项，讲清怎么从 Demo 到可分享链接）

项目除了本地跑，还发布到了公网，得到一个 https 链接，面试官打开即可体验，无需装环境。

**部署形态**：FastAPI 作为一个 HTTP 服务发布到沙箱，监听平台注入的 `PORT` 环境变量、绑定 `0.0.0.0`。

**为部署做的两处改造（面试可讲）：**

1. **去掉 Redis 依赖**：部署沙箱只有一个 HTTP 端口，不提供缓存服务。虽然 Redis 是可选的，但配置文件里的示例连接串会被部署工具误判为必需外部服务。于是在部署副本里把会话存储改成纯内存版——这也符合「无外部服务、开箱即跑」的部署要求。
2. **新增 `server.py` 启动入口**：沙箱里 shell 不会展开 `$PORT`，所以不用 `uvicorn --port $PORT`，而是写一个 Python 入口 `os.environ.get("PORT", "3000")` 直接读取，再交给 uvicorn。这样启动命令就是简单的 `python server.py`。

**部署与本地是两份目录**：
- `E:\shop-agent`：完整开发版（含虚拟环境、测试、文档、Redis 可选）
- `E:\shop-agent-deploy`：为部署精简的副本（去掉大文件和可选依赖）

> 面试说法：「我把它部署成了可分享的 HTTP 服务。为了适配无外部服务的沙箱，我把会话存储收敛到内存，并用 Python 入口读取平台的 PORT 变量，避开 shell 展开的环境差异。」

## 九、补充高频追问（双模式 / 部署相关）

**Q：Mock 和 API 模式你怎么实现的？为什么做两套切换？**
一套运行时状态机（带锁）+ REST 接口做热切换，供网页开关现场演示；一套双击脚本改 `.env` 设定默认模式。前者改「当前值、即时生效」，后者改「默认值、需重启」，互补。

**Q：热切换为什么要用锁？**
FastAPI 是异步并发的，多个请求可能同时读写模式状态。用 `threading.Lock` 保证 `get/set` 的原子性，避免竞态。

**Q：切模式会不会影响正在进行的会话？**
不会。模式只决定下一次 `llm.chat` 走 Mock 还是真实接口，会话历史存在 memory 里与模式无关。

**Q：线上切到 API 模式，Key 从哪来？**
部署时写进了环境的 `.env`（已 gitignore，不进代码仓库）。切 API 时 `set_mode` 会检查 Key 是否存在，没有则拒绝切换。

**Q：为什么 Mock 模式响应特别快？**
它不发网络请求，直接用规则引擎匹配关键词、选工具、拼答案，所以是 0ms 级；真实模型要联网推理，通常几秒。评测集在 Mock 下 10/10、延迟 0ms，便于确定性验证逻辑。

**Q：部署时遇到的最大问题是什么？**
两个：一是部署工具把 `.env` 示例里的 Redis 连接串误判为必需外部服务，通过精简部署副本解决；二是沙箱 shell 不展开 `$PORT`，通过新增 Python 启动入口读取环境变量解决。这体现了对「开发环境和生产环境差异」的理解。

## 十、最可能被追问的「劝退题」——诚实作答

**Q：这个项目的技术含量在哪？看起来就是调个 API。**
真正的工作量不在调 API，而在：① Agent 循环和边界设计（何时调工具、失败怎么兜底、信息不足怎么追问）；② 把「模型决策」和「数据获取」解耦，用工具返回结构化事实抑制幻觉；③ 可观测性（tool_calls 全链路可展开）；④ 可量化的评测体系，让 Prompt 迭代有依据；⑤ 双模式 + 公网部署的工程完整度。

接入 LangGraph 做更清晰的编排、上流式输出降低等待感、用真实向量库 + 更好的 Embedding 提升召回、加 LLM-as-judge 做更客观的效果评估、会话与工具状态上 Redis 支持多实例。这些在第 11 节「生产化改造」都有对应。

## 十一、MySQL 数据库接入（新增，面试可主动提）

这一节是项目的**数据持久化层**，主动讲能显著加分——因为它把项目从「内存 Demo」升级成「有真实后端存储的应用」。

### 一句话定位

> 「业务数据不硬编码在代码里，而是存在 MySQL。我封装了数据访问层，用开关控制数据源，并做了向本地 JSON 的降级，保证没有数据库的环境也能完整演示。」

### 表结构（4 张表）

| 表 | 关键字段 | 行数 | 谁在用 |
|---|---|---|---|
| `products` | product_id(PK), name, category, price, stock, tags, description | 9 | `search_products` |
| `orders` | order_id(PK), status, amount, logistics, address… | 5 | `get_order` / `create_after_sales` |
| `kb_articles` | id(PK), title, content, tags | 12 | RAG `KnowledgeBase` |
| `after_sales_tickets` | ticket_id(PK), order_id, reason, status, created_at | 运行时写入 | `create_after_sales` |

初始化脚本 `db/init_db.py` 幂等（先 DROP 再建表导入），连接参数从 `.env` 读，密码不进代码。

### 核心设计（三个点，讲清楚就够）

**1. 配置开关 + 优雅降级**
`MYSQL_ENABLED=1` 才连库；`app/db.py` 里每个查询都 try/except，连不上返回 `None`，工具层据此回退 `data/*.json`。所以 Mock 模式、单测、没装 MySQL 的电脑都能跑。**这是容错设计，不是可有可无。**

**2. 实时读库（面试可现场演示）**
`search_products` / `get_order` 每次调用都查 MySQL，不是启动时加载一次。演示方法：当着面试官的面 `INSERT` 一条新商品到 `products` 表，再问客服，立刻能查到——证明数据来自数据库而非写死。

**3. 类型处理**
PyMySQL 返回的 `DECIMAL` 会转 float、`DATETIME` 转字符串，否则 FastAPI 响应序列化会报错。这是接数据库时最常踩的坑之一。

### 数据流（一句话）

`用户提问 → Agent 选工具 → 工具调 db.fetch_all() → MySQL → 结果回填给模型 → 生成回答`，写操作（售后工单）走 `db.execute()` 落库。

### 高频追问

**Q：为什么用原生 PyMySQL 而不是 ORM？**
这个 Demo 的 SQL 很简单（单表查询为主），引入 SQLAlchemy 会增加抽象层和依赖。手写数据访问层更透明，也便于讲清「降级」逻辑。生产环境用 ORM + 连接池更合适。

**Q：每次查询都建连接，性能不差吗？**
Demo 场景并发低，可以接受；而且连接用完即关，避免长连接失效。生产化会换成连接池（如 `DBUtils.PooledDB`）或 ORM 的 session pool。

**Q：知识库的向量也存在 MySQL 吗？**
没有。MySQL 存的是知识库**原文**（`kb_articles`），向量是服务启动时在内存里算的（本地哈希向量化）。生产环境可以把向量换成存 pgvector / Milvus，原文仍可留在 MySQL——这就是「结构化数据和向量数据分离」的常见架构。

**Q：数据库连不上会怎样？**
自动回退本地 JSON，功能不受影响，只是数据不是最新的。健康检查里 `mysql_connected: false` 会提示这个状态。
